```
三条核心线：
  Canon v2.7.2 (典则线)     → 规则生产库。只管规则从哪来、怎么固化。
  Guard v4.8.3 (护栏线)     → 规则执行器。AI 读规则自觉遵守，pre_action 五道闸。
  Mnemonic v3.5.3 (忆存线)  → 状态记忆。记录错误、提取模式、数据源管理。

一条外观：
  CMG v5.6.0               → 统一引擎。四包制分装 + Dashboard + 诊断/协调。

两个插件：
  sentinel v1.4.0         → 硬拦截层。17个Hook，真正"拦"的那一层。

配套工具：
  Dashboard v1.0.0         → Web 可视化管理（localhost:8765）
```

## 一、审计结论

### 1.1 三条核心矛盾

| # | 矛盾 | 严重度 | 当前状态 |
|:--:|------|:--:|------|
| 1 | 9/69 规则无硬拦截（gap/lazy/meta） | 🔴 | v5.6.0 清理后 gap12→4 lazy9→3，总量82→69 |
| 2 | CLI/GUI CMG 功能不等效 | 🟡 | v1.4.0平台检测是妥协，非根治 |
| 3 | 事后拦截模型依赖CLI交互循环 | 🟡 | 架构级限制，需转向事前注入 |

### 1.2 不动的硬边界

- LLM 100%约束不可能（数学问题，非工程问题）
- 思考链不可拦截（管得了输出管不了推理）
- transform_* 钩子 GUI 先天不兼容（无交互循环）

### 1.3 修正方向确认

和用户讨论后达成一致的三条升级原则：
1. **不修钩子兼容性→改钩子策略。** 从事后替换转向事前注入
2. **gap/lazy/meta 不能继续靠自觉。** 需要行为级检测器
3. **CLI 和 GUI 同步升级。** 新能力两个平台必须同时受益

### 第二阶段：sentinel v1.5.0 — 双向升级

> **目标：** CLI 和 GUI 同步受益，不新增平台不对称的能力。

#### 2.1 pre_llm_call 注入活跃规则（CLI+GUI 同等）

```
现在：AI 在系统提示里读 SKILL.md → 60条规则全在上下文 → 靠记忆遵守
升级：
  每次 LLM 调用前，pre_llm_call 按任务类型匹配最相关的 5-10 条规则
  → 结构化注入 system prompt 末尾：
  
  ═══════════════════════════════════════
  本次任务活跃约束:
  [ban] 发布前必须 grep 版本号 — 当前打包任务
  [ban] 禁止虚构技能 — 你在做安装
  [gap] 安装后必须验证文件存在 — 当前安装任务
  ...
  ═══════════════════════════════════════
```

要点：
- 不是灌 82 条，是精准给 5-10 条最相关的
- 按 task_recommendations 已有的任务关键词做规则匹配
- CLI 和 GUI 都通过 pre_llm_call 注入，同一条路径

#### 2.2 强化 pre_llm_call 哨兵（GUI 端补齐）

```
现在：GUI 端哨兵静默（检测纠正 + 写 errors.jsonl，不注入）
升级：
  哨兵检测到纠正 → errors.jsonl 写入 → 标记 session_state
  → 下次 pre_llm_call 加载上次违规记录 → 注入 "注意：上次你违反了 X 规则"
  
  CLI: 实时提醒 (现有) + 跨会话提醒 (新增)
  GUI: 跨会话提醒 (新增)
```

GUI 端虽不能实时注入 `[CMG-SENTINEL]`，但下次会话可以提醒。比现在的"完全静默"强。

### 第三阶段：sentinel v2.0.0 — 根治

> **目标：** 消除 gap/lazy/meta 的自觉依赖 + 给 GUI 真正的重试能力。

#### 3.1 行为级检测器（gap/lazy/meta 专用）

```
gap 检测器 (步骤完整性):
  任务开始 → 提取步骤清单 → 每步完成后标记
  → post_llm_call 检测: 声称"完成"但步骤清单有未完成项 → 拦截

lazy 检测器 (工作流合规):
  特定任务类型（打包/安装/创建skill）→ 匹配 checklist
  → post_llm_call 检测: 跳过必要步骤 → 拦截

meta 检测器 (能力越界):
  post_llm_call 检测: "我能..." "支持..." → 对照 Hermes 实际能力
  → 承诺了不存在的能力 → 拦截
```

这 22 条规则不再靠 AI 自觉 → sentinel 接管。

#### 3.2 自动重试闭环（解决 GUI 最大短板）

```
post_llm_call 检测到违规
  → 不替换输出（不依赖 transform_llm_output）
  → 追加 system 消息: "上一轮输出违规。违规点: X规则。请重新生成。"
  → 同一请求流程内触发 LLM 重新生成
  → 最多重试 3 次
  → 用户只看到最终合规版本

CLI: 不再需要 AI 看到替换文本再重试 → 更快
GUI: 首次获得重试能力 → 追平 CLI
```

关键：不依赖外部交互循环，sentinel 自己完成"检测→纠正→重试"。

#### 3.3 三层验证管线

```
LLM 输出
    ↓
合规层 (现有 ban 关键词 + 新增 gap/lazy/meta 行为检测)
  通过 → 继续
  不通过 → 自动重试 (最多 3 次)
    ↓
完整层 (步骤是否全部完成)
  通过 → 继续  
  不通过 → 注入缺失步骤 → 重试
    ↓
一致层 (前后回答是否自相矛盾)
  通过 → 输出
  不通过 → 注入矛盾 + 重试
```

## 五、风险矩阵

| 风险 | 概率 | 影响 | 缓解 |
|------|:--:|:--:|------|
| 自动重试触发无限循环 | 中 | 高 | 硬上限3次重试，第4次原样输出+标记 |
| 行为级检测器误判 | 高 | 中 | 初期只报警不拦截，跑2周校准后再启用拦截 |
| Hermes钩子不支持触发重试 | 低 | 高 | 降级为追加system message让LLM自发重试 |
| pre_llm_call注入过长导致token浪费 | 中 | 中 | 每次注入≤500 tokens，超过按相关性截断 |
